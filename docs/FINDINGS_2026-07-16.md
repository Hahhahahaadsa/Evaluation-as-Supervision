**Scope:** data distribution, information flow between agents, orchestrator
role, evaluation coverage, dataset utilisation, and documentation drift.

## F1 — P0 — Statistical claims are unqualified on a median sample of 15 reviews

**[measured]** Actual review counts per business in the local DB (150,346
businesses with at least one review):

| percentile | reviews | | threshold | businesses | share |
|---|---|---|---|---|---|
| p10 | 6 | | >= 10 | 101,270 | 67.4% |
| p25 | 8 | | >= 20 | 63,489 | 42.2% |
| **p50** | **15** | | >= 50 | 30,181 | 20.1% |
| p75 | 38 | | >= 100 | 15,291 | 10.2% |
| p90 | 101 | | >= 300 | 3,578 | 2.4% |
| p99 | 492 | | >= 1000 | 346 | 0.2% |

Half of all businesses have 15 or fewer reviews.

**[code]** `Pattern.frequency` (`app/schemas/contracts.py`) is a proportion, and
`eval/tier1_checks.py:182` recomputes it as `negative_count / total_success`.
It is a sample statistic. Nothing in the pipeline records or propagates the
denominator `n`, and nothing computes a confidence interval.

At n=15, one review moves `frequency` by 6.7 percentage points. A reported
`frequency: 0.33` carries a 95% confidence interval roughly spanning 13%–60%,
which is indistinguishable from noise. The system emits that number with two
decimal places and `confidence: "high"`, in exactly the same tone it would use
for a business with 500 reviews.

The number then propagates: `app/agents/strategy_agent.py:85-88` sorts
recommendation priority by `frequency`. For a median business, the order of
actions presented to the owner is decided by noise.

**Impact.** For >50% of businesses the reported statistics are not defensible.
This is the most severe finding in this document because it affects the majority
case, is invisible to the user, and no existing check detects it.

**Suggested direction.** Propagate `n` through `ReasoningOutput`, compute a
confidence interval per pattern, and require the report to state uncertainty or
decline to conclude. Applies to 100% of businesses, unlike any time-series
approach.

## F2 — P1 — The Reasoning agent is given the task it is worst at, and denied what it needs for the task it is best at

This is the central finding about the Reasoning agent. It has two halves that
compound.

### F2a — It must produce a statistic by counting, unaided

**[code]** The prompt (`app/agents/reasoning_agent.py:6-23`) requires:

> *"frequency: **proportion of reviews (0.0–1.0)** that mention this aspect
> negatively"*

The LLM is asked to count occurrences across a list and divide. LLMs are
unreliable at exactly this. The team evidently knew: `eval/tier1_checks.py:177-185`
recomputes the same number in Python and compares it to what the model claimed,
with a 0.05 tolerance.

So the current design is:

```
LLM guesses frequency  →  Python recomputes it  →  Python checks the guess
```

Python already computes the correct value. The guess adds a failure mode and no
information. `frequency` is derivable from `analysis_results` with certainty and
at zero cost:

```python
negative_count / total_success        # tier1_checks.py:182 — already written
```

**Impact.** An entire class of hallucination exists only because a deterministic
computation was delegated to a language model. It also blocks F1: Python knows
`n`, the LLM does not, so no confidence interval can exist while the model owns
the number.

### F2b — It must infer causes without evidence

**[code]** `app/core/nodes.py:98-106` forwards only `review_id`, `sentiment`,
and `aspects`. The string `"text"` appears exactly once in `nodes.py`, at line
73, inside `analysis_node`. `AnalysisOutput` (`contracts.py:39-44`) retains
neither `text`, `date`, nor `stars` — so all three vanish at the analysis
boundary even though `state["reviews_df"]` still holds them.

The same prompt asks the agent to identify "root causes". Reading text and
proposing explanations is what an LLM is genuinely good at. It is given a label
table instead, and cannot know *why* anything happened. `RootCause.cause` is
therefore inferred from aspect statistics.

**Corroborating evidence:** `eval/tier1_checks.py` verifies three properties of
`patterns` but contains **no check at all for `root_causes`** — see F5. Not an
oversight: root causes are currently ungroundable because no text survives to
compare against.

### Combined

| | LLM strength | What the agent is asked to do |
|---|---|---|
| `frequency` | weak (arithmetic) | **must produce it** |
| `root_causes` | strong (reading text) | **must produce it without text** |

The division of labour is inverted on both axes. Fixing it means swapping them:
Python computes the numbers, the LLM reads the prose.

**Suggested direction.**

1. Remove `frequency` from the reasoning agent's output contract; compute it in
   `reasoning_node` from `analysis_results`, carrying `n` alongside (unblocks F1).
2. Join `text` from `state["reviews_df"]`, restricted to reviews carrying a
   negative aspect to bound tokens.
3. Add `evidence_review_ids` to `RootCause` in `contracts.py` (unblocks F5).

Note that (1) *removes* a field from an agent contract — a contract change
requiring an entry in `docs/DECISIONS.md`.

## F3 — P1 — The Reasoning agent never sees dates either

**[measured]** The `date` column is fully populated to second precision
(`2018-07-07 22:09:11`), spanning 2005-02-16 to 2022-01-19 across 6,990,280
reviews.

**[code]** `reasoning_node` drops `date` along with `text`. `analysis_node`
passes it to the analysis LLM (`nodes.py:73`) but the analysis contract does not
retain it, so it never reaches any downstream stage.

**Impact.** No temporal reasoning is possible. The system cannot distinguish a
long-standing baseline problem from a recent regression — a distinction that
changes what the owner should do.

**Caveat [assessed].** `date` is when the review was *written*, not when the
visit occurred. Hour-of-day analysis is not defensible on this data.
Month/year trends and changepoints are.

## F4 — P1 — No stage validates output quality; only technical failure

**[code]** Every routing function (`app/core/graph.py:15-35`) branches on one
condition: `status == "error"`. And `status: "success"` means only that
`json.loads()` succeeded and Pydantic validated
(`app/agents/base_agent.py:104-110`).

A fabricated but schema-valid output — invented frequency, invented root cause,
self-assigned `confidence: "high"` — is `success`. The error handler never runs.
The orchestrator is never consulted.

Every defensive mechanism in the system (retry, model fallback, orchestrator
recovery, critical-agent downgrade) protects against *breaking*. None protects
against *being wrong*.

**Note.** The logic to detect fabrication already exists in
`eval/tier1_checks.py` — it recomputes frequency, resolves evidence IDs, and
checks aspect alignment. It runs offline, after the fact, against a dump
directory. `README.md:209` already lists "enforce evidence and frequency
grounding before returning an API response" as pending.

**Suggested direction.** A deterministic validator node between reasoning and
strategy, holding `state` (so it knows `n`), reusing the `tier1_checks` logic.
No LLM required.

## F7 — P1 — Architecture drift: the Orchestrator was designed as a hub, built as an exception handler

**Intended design (team, stated 2026-07-16).** The Orchestrator is the
transit station between every agent — it holds control at all times and hands
off to each stage in turn:

```
orchestrator -> analysis -> orchestrator -> reasoning -> orchestrator -> report
```

**As built** (`app/core/graph.py:109-135`). A linear chain with the
orchestrator reachable only from a failure branch:

```
preprocess -> analysis -> reasoning -> strategy -> report -> END
                  |            |           |          |
                  +------------+-----------+----------+
                               v  (only when status == "error")
                        error_handler -> orchestrator
```

This is not a missing feature; it is **drift between the agreed architecture and
the implementation**. On a successful run the intended hub is never entered.

Three independent reasons the current implementation cannot be made to hold
control, each sufficient on its own:

**[code] 1. It is unreachable on a successful run.** Every routing function
(`graph.py:15-35`) branches on one condition, `status == "error"`. On a clean
pipeline `error_handler` is never entered and `decide_recovery()` is called
**zero times**. Control passes agent-to-agent without the orchestrator being
consulted.

**[code] 2. Its signature cannot carry a supervision decision.**

```python
def decide_recovery(self, failed_agent: str, error_detail: str, retry_count: int) -> str:
```

(`orchestrator.py:43`) — no `state`. It cannot see the review count, the
analysis results, or any agent output. Even if it were invoked on every
transition, it has nothing to supervise *with*. Note the name: `decide_recovery`,
not `decide_next`. The contract is recovery, not control.

**[code] 3. Its return values only describe failure.** `retry | skip | halt`
are all responses to something going wrong. There is no verdict meaning
"proceed", because proceeding is what happens when the orchestrator is *not*
called. A supervisor whose vocabulary has no word for "continue" cannot own the
happy path.

**[code] Secondary:** `_get_llm()` (`orchestrator.py:26-34`) resolves through
`llm_config.primary_model()` — the same provider the agents use. When that
provider fails, the supervisor fails with it and falls back to a hardcoded
`"retry"` (`:70`). Bounded by `MAX_RECOVERY_RETRIES` and regression-tested, so
not a live defect, but a supervisor should not depend on the component it
supervises.

**[assessed] Related:** the LLM's decision space is already narrow. For a
critical agent with retries left, a `skip` verdict is downgraded to `halt` by
`graph.py:90`, and an invalid or failed response becomes `retry` (`:70,74`) —
outcomes are largely determined by hard rules. An LLM call is being paid for on
a decision that `if` statements mostly make.

**The documentation has normalised the drift.** `README.md:159` describes the
Orchestrator as "Retry, skip, or halt decisions **after stage failure**", and
`README.md:261` repeats "the orchestrator chooses retry, skip, or halt". Both
describe the *implementation* accurately. Neither records that the agreed design
was a hub, so nothing in the repository reports the gap — the docs were
back-fitted to the code until the intended architecture disappeared from the
written record.

This contradicts `AGENTS.md:77`, a binding rule: *"Distinguish agreed target
behavior from current implementation behavior."* That rule exists precisely to
catch this, and here it was not applied. Restoring the hub therefore means
updating `AGENTS.md`, `README.md`, and adding an entry to `docs/DECISIONS.md`
(append-only) — the intended design should be on the record even before the code
matches it.

Corroborating trace of the drift: `AGENTS.md:48` still places the Orchestrator
in `backend/app/agents/`, alongside the other agents — which is where a hub
would belong. It actually lives in `backend/app/core/orchestrator.py`, next to
the graph machinery. The file moved to match its reduced role; the document did
not.

**Suggested direction — supervisor pattern.** Route every transition through
the orchestrator instead of only the failure branch:

```
analysis → validator → ORCHESTRATOR → reasoning → validator → ORCHESTRATOR → strategy → ...
```

Requires three changes:

1. **Split measuring from deciding.** A deterministic validator (F4) computes
   the facts — `n`, recomputed frequency, evidence resolution. The orchestrator
   consumes those facts and decides. The validator may not decide; the
   orchestrator may not compute (it would guess).
2. **New signature** carrying `state` and the validator's report — not the three
   scalars it takes today.
3. **Extend the verdict set** beyond `retry | skip | halt`:
   - `proceed` — normal continuation, now an explicit decision on the record
   - `proceed_with_warning` — e.g. n=15 (F1): continue but flag the stage
     `low_confidence` so the report must disclose it
   - `retry` / `skip` / `halt` — as today

Cost: the orchestrator runs ~4x per pipeline instead of ~0. It stays free if
routine verdicts are hard rules over validator output, escalating to an LLM only
for genuinely ambiguous cases. That also removes the provider dependency above
for the common path.

This is the only proposal in this document that gives the orchestrator work on
every run, and `proceed_with_warning` is what makes F1 actionable rather than
merely reported.

## F8 — P2 — The DB discards 12 of 23 available Yelp fields

**[measured]** Raw file fields vs. what `scripts/build_db.py` imports:

| source | imported | discarded |
|---|---|---|
| `business.json` (14) | business_id, name, address, city, state, review_count | **stars** (avg), **categories**, **is_open**, **hours**, attributes, latitude, longitude, postal_code |
| `review.json` (9) | review_id, business_id, stars, text, date | **useful**, **funny**, **cool**, user_id |

Most consequential:

- **`categories`** — without it, no peer-group comparison is possible. This
  blocks any "compared to similar restaurants" benchmark.
- **`is_open`** — a free ground-truth label, while `README.md:371` reports Tier 2
  as still awaiting manual labelling.
- **`useful`** — community signal on review quality. Sampling currently treats
  all reviews as equal.
- **`stars` (business avg)** — no baseline to compare against.

**Cost is asymmetric [measured].** `business.json` is 118 MB (rebuild: seconds);
`review.json` is 5.3 GB (rebuild: minutes, one-off). `main()` rebuilds both
together; a `--businesses-only` flag would make the high-value half nearly free.

**[code]** `nodes.py:146` passes `"analysis_summary": {}` and

## F10 — P2 — The analysis failure threshold silently discards up to 50% of data

**[code]** `route_after_analysis()` (`graph.py:15-20`) escalates only when
*more* than 50% of reviews error. At exactly 50%, the pipeline proceeds;

Compounding with F1: on a 15-review business, 7 failed analyses leave 8 reviews

## F13 — P2 — The Analysis agent discards a free verification signal, and fails in blocks of ten

The Analysis agent is the most reliable stage in the pipeline: it classifies
each review independently, so unlike Reasoning it is unaffected by sample size
(F1). Its output is also the only stage with objectively checkable answers, as
`eval/tier2_analysis.py:3` correctly notes. Two issues nonetheless.

### F13a — `stars` is never used to verify `sentiment`

**[code]** Every review carries `stars` (1-5), assigned by the customer who
wrote it. It reaches the analysis LLM (`nodes.py:72`) and then disappears:
`AnalysisOutput` (`contracts.py:39-44`) does not retain it, and no check
anywhere compares it to the predicted `sentiment`. A grep for `stars` across
`app/` and `eval/` finds only loading, clipping, and fetching — never a
comparison.

The team already identified the idea and wrote it down. `eval/tier2_analysis.py:11`:

> *"Star rating is only a noisy cross-check (5 -> positive, 1-2 -> negative),
> NOT ground truth."*

That judgement is **correct** and should not be reversed — a 4-star review can
legitimately carry a negative aspect, so stars cannot serve as sentiment labels.
But the cross-check the docstring describes was never implemented. `stars` is
fetched at `tier2_analysis.py:79-90`, placed in the review dict, and then plays
no part in `score_sentiment()`.

**What it is worth.** Not a replacement for Tier 2 gold labels. But *flat
contradictions* are checkable for free, offline, across all 6,990,280 reviews:

| stars | predicted sentiment | reading |
|---|---|---|
| 5 | `negative` | near-certain model error |
| 1 | `positive` | near-certain model error |
| 4 | `mixed` (aspect negative) | legitimate — not a contradiction |
| 3 | anything | no signal |

Meanwhile `README.md:371` reports Tier 2 as blocked awaiting manual labels on
40 reviews. A contradiction rate needs zero labels and zero API calls, and can
run inside the pipeline (F4's validator) rather than only offline.

### F13b — One failed batch discards ten reviews

**[code]** `ANALYSIS_BATCH_SIZE = 10` (`nodes.py:25`). On batch failure,
`run_batch()` (`analysis_agent.py:95-104`) returns one `AgentError` **per review
in the batch** — so a single bad LLM response costs 10 reviews, not 1.

Interaction with F1 and F10 on a median (15-review) business: reviews split into
batches of 10 and 5. If the second batch fails, 5 of 15 reviews are lost — 33%,
which is **below** the 50% escalation threshold (`graph.py:18`). The pipeline
proceeds silently on 10 reviews while the report still states `sample_size: 15`.

**[assessed] Related trade-off, not a defect.** `validate_batch()`
(`analysis_agent.py:81-86`) requires returned IDs to equal input IDs *in order*
(`actual_ids != expected_ids`). Per `PROJECT_AUDIT.md:138-142` this is
deliberate: one comparison enforces count, membership, ordering, and duplicate
detection. The cost is that a semantically harmless reordering fails the whole
batch through all retries. Order carries no meaning here — `review_id` is the
key — so set-equality plus a reorder would be equally strict on what matters and
cheaper on what does not. Recorded for the team to weigh; the current choice is
defensible.

## Suggested order

Ordered by dependency, not by severity alone. F2b unblocks F5; F2a unblocks F1;
F4 unblocks F7.

1. **F2a** — move `frequency` out of the LLM's contract and compute it in
   `reasoning_node` from `analysis_results`, carrying `n`. Deletes a
   hallucination class outright and is the prerequisite for F1.
2. **F2b + F3** — forward `text` and `date` in `reasoning_node` (~15 lines).
   Same code site as (1); do them together. Prerequisite for F5.
3. **F1** — confidence intervals over the now-exact `frequency`; let the report
   say "insufficient evidence". Highest severity; affects the majority case.
4. **F12** — write `docs/LOCAL_LLM.md`; correct the stale index status.
   Cheap, and the missing file is graded coursework evidence.
5. **F13a** — contradiction check between `stars` and predicted `sentiment`.
   No labels, no API calls; usable both offline and inside F4's validator.
6. **F8** — add `--businesses-only` plus `categories`, `stars`, `is_open`,
   `hours`. Seconds to rebuild; unblocks peer-group comparison.
7. **F4 + F5** — validator node reusing `tier1_checks` logic; add a root-cause
   groundedness check. **Prerequisite for F7**: without it the orchestrator has
   no facts to supervise with, and would only be guessing more often.
8. **F7** — restore the hub: route every transition through the orchestrator;
   new signature, extended verdict set. Consumes F4's validator output and F1's
   `n`. Architectural change — record the intended design in `AGENTS.md`,
   `README.md`, and `docs/DECISIONS.md` first, ideally before the code lands.
9. **F11 + F13b** — code-level cleanups and the batch-size trade-off,
   independent of the above.

## Limitations of these findings

- No live LLM request was made. No claim here rests on observed model output;
  F1 and F2 are arguments about what the code *can* know, not measurements of
  what it produced.
- Confidence intervals in F1 are stated approximately and should be recomputed
  with a chosen method (Wilson recommended) before quoting in a report.
- F6 is an observation about design emphasis, not a defect. It is recorded
  because it affects where effort is best spent, and is the most open to
  disagreement.
- F7 was initially filed as a P2 design observation, on the assumption that
  error-recovery was the Orchestrator's intended scope. That assumption was
  wrong: the team stated on 2026-07-16 that the agreed design was a hub
  (`orchestrator -> analysis -> orchestrator -> ...`). It is therefore a P1
  architecture drift, not an observation. The intended design is recorded here
  from the team's statement; it does not appear anywhere in the repository, so
  this document is currently its only written trace. If the hub was never
  formally agreed, F7 should be re-filed as a proposal rather than a drift.
- F13a recommends using `stars` as a contradiction check only. It is **not** a
  proposal to treat stars as sentiment ground truth — `eval/tier2_analysis.py:11`
  already rejects that, correctly, and that judgement should stand.
- The claim in F2a that Python can compute `frequency` exactly assumes the
  reasoning agent's definition ("proportion of reviews mentioning this aspect
  negatively") is the intended one. `eval/tier1_checks.py:177-181` already
  encodes that reading. If the team means something else by `frequency`, F2a's
  remedy needs revisiting — but then the existing Tier 1 check is also wrong.
- The peer-group comparison implied by F8 is untested. The 2020 COVID effect is
  a confounder: reviews fell 39% industry-wide (907,284 in 2019 -> 554,557 in
  2020) **[measured]**, so any changepoint near 2020 requires a control group.
